# Twin Ops — a commissioned digital twin, end to end

**HX-201, a fouled shell-and-tube exchanger.** The example exists to show the whole product,
not a plot: a signed contract, a preflight that can refuse, a held-out backtest, an evidence
file, and a drift ladder for when the plant moves away from the model.

```bash
python apps/twin_ops/demo.py
```

## What the twin does that a dashboard does not

The exchanger model knows the geometry, the flows and the clean rating. It does not know the
**fouling resistance** — nobody measures it, it builds up over months, and it decides when the
exchanger is cleaned. The twin estimates it from the temperatures and flows the plant already
has, and says how far it is from the limit and how long that took to become true.

## The five pieces

| file | what it is |
|---|---|
| `spec_hx201.yaml` | the contract: fields, sensors in which units, drivers, acceptance gates. It has a digest; every report is filed under it. |
| `twin_ops/exchanger.py` | the plant (ε-NTU with fouling, plus a flow-dependent UA the model ignores) and a 72 h history generator |
| `demo.py` | commission → put on line → write evidence |
| `twin_evidence_hx201.json` | the artifact you hand over |

The reusable machinery lives in the library:
`pinneapple_systems/digital_twin/product/`.

## How this relates to `apps/twin_runtime`

They are two halves of one product line and they do not overlap.

**`apps/twin_runtime`** (day 20) is the *runtime*: EnKF over a lumped tank or an operator-
inference surrogate, forecasts with 5–95 % bands, alerts on hysteresis rules including a
normalised-innovation χ² test, `pp.assess_drift` validity checks with revalidation, SQLite or
Postgres history, MQTT, REST and experimental OPC UA. Its library home is
`pinneapple_systems.operations`.

**`pinneapple_systems.digital_twin.product`** is the *commissioning layer* that runtime does
not have: a signable spec with acceptance gates and a digest, an 11-item preflight that can
refuse before the twin ever runs, a backtest against a held-out instrument, an evidence file,
and a drift ladder expressed as a policy rather than a rule list. It is model-agnostic — any
`model(X, theta)` works, including a `ModelRef`-backed surrogate.

`twin_ops` is this layer's reference example. Pointing the runtime at a commissioning spec is
the natural next step and is not done here.

## The result on the reference run

| | |
|---|---|
| preflight | 11 checks, 0 fail, 0 warn |
| out-of-sample RMSE | **0.216 °C** — 0.54 % of the 40 °C span |
| bias | −0.010 °C |
| band coverage (scored window) | **95.5 %** of held-out readings inside the band |
| fouling estimate | **0.001651 ± 0.000010 m²K/W** against a true 0.001637 (0.9 %) |
| alarm lead | **9,300 s (2.6 h)** before the measurement crossed the limit |
| forecast error | the projected crossing landed 3,900 s (1.1 h) from the crossing that happened |

## Three things this example is honest about

**The band is calibrated on a separate window.** The filter's ensemble spread is a band on its
*state*; it does not contain the noise of the assimilated channels, which propagates into the
estimate. Commissioning therefore measures one multiplicative band scale on the first half of
the scored window and reports coverage on the **later** half. Export shows both numbers: the
raw band covered 86.4 %, the calibrated one 95.5 %, scale ×1.34. Fitting the band on the data
it is scored on would have produced a meaningless 95 %.

**The lead comes from a projection, and the projection is measured.** A now-cast twin — "the
estimate is over the limit right now" — can only ever be minutes early, because it is a
smoothed copy of the measurement. The alarm here extrapolates the latent state linearly and
fires when the field is projected past its limit within `warn_horizon_s`. Linear extrapolation
of a saturating fouling curve overshoots, which is exactly what the reported 1.1 h forecast
error shows.

**Everything is synthetic, and says so.** The history is generated by `exchanger.py` from
standard engineering correlations, not measured on a plant. The evidence file carries
`"demo on synthetic history; not a plant commissioning record"` in its notes.

## Wiring it to a real asset

1. Write the spec: fields with engineering limits, sensors with units and envelopes, one
   redundant instrument marked `holdout: true`, one latent parameter per unknown.
2. Point the model at your own `model(X, theta)`; if you only have `model(X)`, wrap it in
   `BiasModel` and the latent state becomes one offset per field.
3. Commission on a few weeks of history. If preflight fails, the checklist says which file,
   which channel and what to change.
4. If the backtest fails, do not lower the gates — the report says which gate and by how much.
5. Ship `twin_evidence_hx201.json` with the twin, and re-commission on a schedule: the
   evidence has a date on it.

## Publishing the twin

`describe(spec, latent, fields)` returns a `TwinDescription`, which the platform's
`standards` module turns into AAS (needs the BaSyx Python SDK), DTDL, NGSI-LD or an Eclipse
Ditto thing, so the plant's own platform can consume the twin without a bespoke integration.
`OpcUaTwinServer` serves the same values over OPC UA for SCADA and MES.
