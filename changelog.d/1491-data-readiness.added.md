- The data-readiness gate (issue #1491, part of the PDI program #1497): `pinneapple_data.readiness.readiness(subject, table=..., case_files=..., policy=...)` assesses a dataset and returns a report with a **verdict** (`PASS` / `WARNING` / `FAIL` / `NOT_ASSESSED`), a score with its published formula, and findings that each carry an id, a group, the evidence and a fix. It composes what the library already had instead of re-implementing it — `physical_units` for the units (declared and against the table header), the manifest for schema/conditions/validity, `data_health.analyze` for the table and `preflight` for a solver case. `require(report, review=...)` is the gate: `FAIL` and `NOT_ASSESSED` never train, `WARNING` trains only with a review record (`pinneapple_data.review`, #1493) that accepts **exactly those findings for exactly this digest**, and `Trainer(readiness=report, review=store)` refuses before the first epoch and carries the verdict, the digest, the record id and the reviewer into the run it returns. The **verdict is not the score** — two datasets scoring 70 are `FAIL` and `WARNING` respectively, asserted in the tests. The digest covers the manifest *and* the data, so changing one value invalidates an approval. Review records are append-only and chained (`ReviewStore.verify()` detects an edited or removed record), an `accept_exception` has to name the finding ids and the reason for each, and a record cannot be built without a reviewer. Nothing changes when no report is given: `Trainer` without `readiness` behaves exactly as before. Example, with the full path assess → refuse → review → train: `examples/data_readiness/`.
