- `PhysicalProblem` grows the façade the strategy asks for (issue #151, item S2 over the reconciled spec of #150): `objectives` (`Objective`: a quantity to minimise, maximise or drive to a target, with a weight and a unit), `constraints` (`Constraint`: a bound `T <= 350 K` or an expression, each printing the same one line through `.text()` wherever it appears), `fidelity` (`Fidelity`: the physics level — closed_form/linear/rans/les/dns/surrogate — the mesh level and the relative tolerance, summarised by `.describe()`) and `geometry_ref` (a path or URI to the CAD or mesh the domain came from). The three types validate themselves where they are set — an unknown `sense`, a target objective with no target, a bound with no value, a non-positive weight — instead of failing later inside a solver. The façade is carried by `to_dict`/`from_dict` (so a saved `Experiment` reproduces the question, not just the physics), by the PDE spec (`spec.meta["facade"]`, read back by `from_pde_spec`) and by the elicited design (`to_problem_design` puts the constraints in as text and uses `geometry_ref` for the domain and the fidelity for the representation) — one problem, set once, compiling into both specs without re-entering data. The keys are emitted only when set, so no existing preset changes its fingerprint. Exported as `pp.Objective`, `pp.Constraint` and `pp.Fidelity`.
