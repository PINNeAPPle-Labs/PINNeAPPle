- `pinneapple_neural.physics_model` gives the five model families one interface (issue #155, item S6): `PhysicsModel` answers `fit`, `predict`, `uncertainty` and `export` whatever the architecture, and `as_physics_model(model)` picks the adapter for what it is given — a `PINNBase`, a `NeuralOperatorBase`, a `GraphModelBase`, a `ROMBase` or a `HybridSurrogatePhysics`; an object outside those five is refused with a message naming them. The adapter calls the family's own `forward` and unwraps its dataclass (`PINNOutput`, `OperatorOutput`, `GraphOutput`, `ROMOutput`), so `predict` returns exactly the numbers the family returns, and the gradient fit runs the existing `Trainer`. `FitReport` says which kind of fit it was: `closed_form` for the ROM family (a basis, a linear operator, a sparse regression — no descent, no loss curve) and `gradient` with the per-epoch history for the rest. `capabilities()` states in advance what the instance can honestly do, and the call refuses rather than fabricating: `uncertainty` by Monte Carlo dropout is refused for a model with no hidden `nn.Linear` and no `nn.Dropout` (a `FNO2d` has zero of both, so the spread would be exactly zero, not an uncertainty) and for a ROM, which is a deterministic projection — both name `method="ensemble"` as the route that does work. `export` writes TorchScript (trace of a one-tensor-in graph), ONNX when the `onnx` package is there, or `state_dict`; a graph model, which takes a `GraphBatch` and no flat tensor, is refused in TorchScript with the reason instead of writing a file that looks exported. 45 contract tests in `tests/pinneapple_neural/test_physics_model_contracts.py` hold the five families to the same calls, measure that a gradient fit reduces the loss on its own history (about 13x over 150 epochs on the PINN regression) and that TorchScript reloads and reproduces the prediction.
