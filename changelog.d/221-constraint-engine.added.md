One constraint object applied in training, in an optimizer and in a deployment guard (#221, roadmap X34): `pinneapple_physics.constraint_engine` checks a single `pp.Constraint` with a single arithmetic -- `g <= 0` satisfied, `g` the signed margin over a bound or over a safe-evaluated expression -- and hands that same object to three places instead of three re-implementations. `Trainer(constraints=...)` adds it to the loss as a differentiable penalty, so the network learns the limit; `optimizer_constraints()` turns it into `ineq`/`eq` for `PhysicsOptimizer`, so the optimizer treats it as a real constraint and not a disguised penalty; `ConstraintGuard` asks it again over the served prediction and refuses the answer that violates a hard one, with the mode `on_violation="report"` for measuring a limit in production before enforcing it. The six families the issue names (`physical`, `conservation`, `operational`, `material`, `actuator`, `safety`) label the constraint -- the report groups by them and the optimizer names its constraint with them -- and deliberately do not change the arithmetic. `pinneapple_data.expressions` gained `residual()` and an `ops="torch"` backend, so an expression constraint keeps its gradient inside the optimizer.
