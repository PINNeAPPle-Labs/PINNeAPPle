- `MeshDynamicsMGN` (autoregressive MGN for transient mesh dynamics) is now in the graph family's registry with its own capabilities — `input_kind="graph_trajectory"`, `expects=["mesh", "trajectory"]`, `predicts=["rollout"]` — so `pp.list_models()` declares what it actually takes and returns instead of the family's generic `graph`/`u` (#231). The variable-size path is real: `flatten_meshes` stacks meshes of different node counts and topologies into one disjoint union (no edge crosses a sample boundary, so the union is exact), and `MeshDynamicsMGN.step_batch` / `loss_batch` / `rollout_batch` / `train_dynamics_batch` train at `B > 1` — measured identical to the per-sample answers to float32 epsilon. `GNNAdapter` learned the same batch convention: `batch["graphs"]` (per-sample graph objects of any size) or `batch["x_list"]`/`edge_index_list` are run as the union through `stack_graphs` and come back padded to `(B, N_max, out)` with a validity mask, for every model in the family, not only this one. `pinneapple_neural.physicsnemo_bridge.mgn_compare` drives this model and PhysicsNeMo's MGN through the same rollout with the same field conventions and reports each one's error and their agreement; without `physicsnemo` installed the report says so (`native_availability()`) and measures the PINNeAPPle side rather than inventing a comparison.
