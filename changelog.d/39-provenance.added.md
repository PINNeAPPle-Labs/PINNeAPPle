- Provenance, and the gate that enforces it (`pinneapple_data.provenance`, `scripts/validate_provenance.py`): a dataset, a run or a model now has to say **what** produced the numbers (`solver`), **which** PINNeAPPle (`library_version`), **which randomness** (`seed`, an integer or the word `deterministic` for a solver that has none), **which exact inputs** (`data_hash`, `sha256:<hex>`) and **which code** (`commit`), plus a `mesh` record — cells and the mesh file hash — when the solver builds one. `problems()` returns exactly what is missing and `require()` raises it; `build_provenance()` fills in the version, the commit, and the hash of a file the caller points at. The rule is applied in three places that cannot drift because they read the same function: the `Provenance` data contract, `ModelCard.validate()` (so `scripts/validate_model_card.py` and `push_to_hub` refuse a card whose numbers cannot be re-derived) and the new `scripts/validate_provenance.py`, which runs in CI over every model card, dataset, study result and model reference in the tree. A `ModelRef` is a pointer, so it is asked for its `uri` instead of a second copy of the record. The seven artifacts already in the repository were migrated with values that are verifiable rather than plausible — the hash of the dataset each zoo model was trained on, the mesh the Ahmed case ran on (207 080 cells, the campaign level), the commit that introduced each file — and `tests/pinneapple_data/test_provenance.py` fails if a new one lands without them. Two consequences worth stating: `pinneapple_hub.verified_card.certify_model()` now seeds the run (`seed=0` by default) and records it, because a card has to say which randomness produced its numbers, and the zoo's `manifest.json` was re-hashed for the four model cards that gained a record (issue #39).
