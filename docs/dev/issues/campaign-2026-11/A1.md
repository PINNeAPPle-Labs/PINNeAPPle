## Summary

The committed ENSO study (`examples/enso_forecasting/`, guide `docs/guides/enso_forecasting.md`, code `pinneapple_systems.time_series.enso`) compares 30 forecasters of the Niño-3.4 SST anomaly under one protocol and reports their skill honestly, but every number in it is a hindcast: the verifying observations already existed when the forecasts were made. This issue adds the one thing a hindcast cannot buy — a forecast written down, hashed and committed before the answer exists — together with the three deficits the guide itself records: the ensemble is a fixed equal-weight mixture, the models are scored on the whole test period rather than by regime, and several documented data limits (no PMEL warm-water-volume product, a fixed 1982–2011 anomaly base with an unremoved +0.05 K/decade trend, thermocline from WOD D20 rather than a reanalysis) were never quantified as a skill penalty.

## Question

Does the model family that wins on hindcast skill still win when its forecast is sealed before verification, and how much of the reported skill survives calibration, regime conditioning and the removal of the documented data handicaps?

## Why run it

- A sealed forecast is the only form of evaluation a forecasting system cannot game; the repository already commits results with SHA-256 manifests for its inputs, so the same discipline can be extended to the output.
- Calibration is where probabilistic ENSO forecasts usually fail, and the existing study says as much (the EnKF ensemble put only 17 % of lead-6 targets inside the central 95 % interval). Fixing dispersion and re-scoring is a real result, publishable as a methods note.
- Regime-conditional skill separates "useful at all" from "useful in the years that matter": an El Niño forecast that is only skilful in neutral years is not the product anyone wants.
- The 3-D case-study render already in the results directory (`figures/`, Blender clip of 1997/98) has an obvious follow-on: the same pipeline applied to a forecast that has no observations yet.

## Physical model

The models are those of the existing zoo, unchanged in form: the recharge oscillator (with seasonal coefficients and multiplicative noise in the best variant), the delayed oscillator, the linear inverse model, the intermediate coupled model (equatorial shallow-water ocean + Gill atmosphere + SST equation), the SST-map CNN in the spirit of Ham et al. (2019), the PINN variants, and the hybrids (physics plus learned correction, EnKF data assimilation, ensembles). No new physics is proposed here; the experiment is about the evaluation protocol and the ensemble construction.

The dimensionless/controlling quantities that decide whether a configuration is admissible at all stay as they are in the study: the Kelvin and Rossby speeds from the shallow-water layer (`sqrt(g'H)` against the solved crossing time), the damping timescale, and the ENSO period. The existing solver checks (`pipeline.solver_checks()`, results in `results/solver_checks.json`) gate any change to the intermediate model, and this issue does not relax that gate.

Deliberately out of model scope: atmospheric stochastic forcing beyond the fitted noise term, ocean biogeochemistry, and any coupling to a general circulation model. The forecast target remains the Niño-3.4 anomaly; ONI is derived, not modelled.

## Geometry and inputs

There is no 3-D geometry in the forecast itself. The inputs are the committed dataset path: NOAA OISST v2.1 AVHRR-only daily 0.25° (Huang et al. 2021), bucket `noaa-cdr-sea-surface-temp-optimum-interpolation-pds`, monthly-averaged on the model grid; WOD thermocline casts binned to D20 along the equator; ERA5 wind stress. Every source file is recorded with its URL and SHA-256 in `examples/enso_forecasting/results/manifests/`, and `dataset.build_dataset(manifests=...)` refuses a download that does not reproduce a recorded hash. That mechanism is the one this issue reuses for the sealed forecast file.

New inputs this issue needs: the PMEL warm-water-volume product (or a documented substitute if it stays unreachable), an ONI/SOI file from CPC as a cross-check of the ERA5 pressure proxy, and the next months of OISST finals as they are published, which is the verification stream.

## What is missing (the work)

1. **A pre-registration writer.** A small module (proposed: `pinneapple_systems/time_series/enso/preregistration.py`) that, given a protocol and an origin list, runs the selected models, writes the forecast plume (origin, lead, mean, spread, model id, config hash) to a deterministic JSON, computes the file's SHA-256, and refuses to overwrite an existing sealed file. It must also record the git commit and the dataset manifest hashes, so the sealed file is reproducible before it is scored.
2. **A scoring-only entry point.** `score_sealed(path, observations)` that opens a sealed file, verifies the hash, and produces the scoreboard when new observations exist. It must fail loudly if the observation window is not yet complete, and it must never write back into the sealed file.
3. **Ensemble calibration.** Weight fitting (EMOS with a spread correction, BMA, or CRPS-optimal weights) on the validation window only, plus the diagnostics that make calibration visible: reliability diagram per lead, PIT histogram, rank histogram, CRPS and log score with bootstrap intervals, and coverage of the central 50/90/95 % intervals.
4. **Regime conditioning.** Skill split by phase at the origin and at the target month (El Niño / La Niña / neutral by ONI thresholds), report the count in each cell, and refuse to report a cell with fewer than a stated number of cases instead of reporting a noisy number.
5. **New families.** An FNO/Transolver/UNO forecaster on SST maps, a GNN on the equatorial waveguide graph, and an LETKF that replaces the under-dispersed EnKF ensemble; each trained under the equal-budget policy so the comparison stays fair.
6. **Limit quantification.** A sensitivity block that reruns the best three models with (a) the trend removed and the anomaly base moved to 1991–2020, (b) the PMEL WWV in place of the D20 proxy, (c) the ONI/SOI cross-check, and reports the skill delta for each change. Where a source remains unreachable, the report states it and quantifies the handicap instead of leaving it as a footnote.
7. **A scoreboard page.** One generated table (markdown and JSON) that exists in two states: "sealed, awaiting verification" and "scored", so the repository can show a pending forecast without pretending it has a result.

## Experiment protocol

1. Fix the data cut and the origin list. The committed dataset ends with the final OISST file for 2026-09; the first origin that cannot have been informed by its targets is therefore 2026-10. Issue forecasts for every monthly origin from that month forward for as long as the campaign runs, at leads 1–12, 15, 18, 21, 24.
2. Rebuild the dataset with the committed manifests and confirm the hashes; abort on any mismatch.
3. Run the retained zoo under the existing protocol; tune only on the validation window, as the study already does.
4. Fit calibration weights on the validation window; freeze them and record them in the sealed file.
5. Write the sealed plume, hash it, commit it with the date and the data cut.
6. When OISST finals for a target month appear, score the corresponding entries, append to the scoreboard, and update the guide. Do not re-tune after the first score; a re-tuned model is a new, separately sealed entry.
7. Rerun the hindcast part (2012–2024 test period) with the calibration layer and the new families, so hindcast and forecast tables always share one protocol.
8. Compute budget: the full study is documented as a few hours on four cores; the forecast-only step is minutes. The added families and the sensitivity block are the cost centre — budget of the order of 100 CPU-hours for the whole issue, split by model.

Seeds: every stochastic component (oscillator noise, ensemble members, network initialisation) takes an explicit seed stored in the sealed file. The plume must be bit-reproducible from the sealed config.

## Baselines, references and verification

Baselines, all already in `forecast_lab`: persistence, climatology, damped persistence, ARIMA and the seasonal naive. The published comparison the guide could not verify (IRI multi-model plume skill) stays unverified and must not be used as a target.

Verification of the machinery before any claim: the solver checks already committed (Kelvin speed 2.69 m/s solved against 2.70 m/s from `sqrt(g'H)`, Rossby −0.86 m/s, Gill solution against closed form, oscillators against eigenvalues) must still pass. Calibration must be verified on synthetic data with a known distribution (sample from a Gaussian, calibrate, and check that the calibration recovers the parameters) before it is applied to ENSO.

The sealed file itself is verified two ways: the SHA-256 is checked at scoring time, and a re-run from the recorded config must reproduce the same plume byte for byte.

## Metrics

- ACC (anomaly correlation) per lead, dimensionless, against the verification anomaly series.
- RMSE and RMSE skill score against persistence, per lead.
- CRPS and CRPS skill score against climatology, in kelvin, per lead.
- Log score, in nats, per lead.
- Reliability: binned observed frequency versus forecast probability for the three equiprobable categories, with the sample count per bin.
- PIT histogram and its deviation from uniform (a scalar summary plus the plot).
- Interval coverage at the 50/90/95 % levels, per lead.
- Regime-conditional ACC, per phase cell, with the cell count.
- Diebold–Mariano statistic with the Holm-corrected p-value, per model pair of interest.
- Spring-barrier ACC: skill for targets in June–August, per lead.
- Sealing integrity: hash match (boolean), reproduction match (boolean).

## Deliverables

- `results/preregistered/<origin>.json` plus its detached hash file, committed before the target month's observations exist, with the git commit id in the filename metadata (not in the filename).
- `results/scoreboard.json` and `results/scoreboard.md`, regenerated by the scoring entry point.
- Calibration figures (reliability, PIT, rank histogram) per lead for the retained models, into `figures/`.
- The regenerated hindcast tables with the calibration layer and the new families, replacing nothing: the old tables stay, the new ones are labelled by protocol version.
- A short methods note in `docs/guides/enso_forecasting.md` describing the sealed protocol, plus a section listing exactly what the sealed forecast did and did not beat.
- A 60-second render of the forecast plume and its verification, produced through the campaign's video pipeline, with the frame provenance that pipeline requires.

## Acceptance criteria

- A sealed file exists whose hash was committed in a commit dated before the first verifying observation of its earliest target month; the commit history proves the ordering and the check is scripted, not manual.
- Re-running the sealed config reproduces the plume exactly (byte-identical JSON after canonical serialisation).
- The calibration layer, tested on synthetic Gaussian forecasts, recovers the known distribution within the stated tolerance; on ENSO it raises the 90 % interval coverage of the ensemble from the recorded 17 % (lead 6, old protocol) into the 85–95 % band, or the report states that it could not and why.
- Every reported skill number has its baseline and its test statistic beside it; no table reports a model as better without the corrected p-value.
- Regime cells with fewer than the stated minimum sample count are reported as insufficient, not as a number.
- The limit-quantification block reports a signed skill delta for each of the three changes, or states that the source was still unreachable and gives the handicap as a bound.
- The guide's "Limits" section is updated in the same PR that adds the results, not afterwards.

## Realizability and evidence class

The subject is established science: ENSO forecasting is an operational activity, and the physics used here (shallow-water equatorial dynamics, the recharge oscillator, data assimilation) is textbook. `PLAUSIBILITY_CLASS`: `established`. Of the six axes, this experiment fills `mathematical_consistency` (solver checks against closed form and eigenvalues), `numerical_stability` (the protocol's purged CV and the reproduction check) and `physical_plausibility` (Kelvin/Rossby speeds, phase portrait, spring barrier) and `uncertainty_sensitivity` (calibration diagnostics and the limit sensitivity block). `experimental_validation` is filled only to the extent that the verifying observations arrive — a sealed forecast that has not yet been verified leaves that axis not assessed, and the report must say so rather than borrow credit from the hindcast. `technological_feasibility` is not assessed: this is not a device.

## Risks and failure modes

1. **The sealed forecast is worse than the hindcast promises.** This is the most likely outcome and the experiment's main value; the failure mode to guard against is quietly re-tuning after the first score. Mitigation: every model version is sealed separately, and the scoreboard keeps the superseded entries visible.
2. **Calibration overfits the validation window.** With monthly data the validation set is small. Mitigation: nested fitting inside the walk-forward protocol, and a reported comparison between in-window and out-of-window calibration parameters.
3. **The new families do not run at equal budget.** An FNO on small maps can beat a CNN simply by being trained longer. Mitigation: `pinneapple_analysis.cost.equal_budget` gates the comparison, and the report states the budget per family.
4. **Data drift between the sealed run and the verification run.** A revised OISST file changes the verification series. Mitigation: the scoring step records the verification file hashes and reports skill against both the final and the preliminary product where they differ.
5. **Spring-barrier claims with tiny samples.** The existing study already shows how noisy that cell is. Mitigation: minimum cell counts and bootstrap intervals, and no conclusion from a cell below the threshold.
6. **A "record-breaking" headline that the statistics do not support.** The guide's own finding is that from lead 3 on no model is distinguishable from climatology on that test period. Any public claim must carry that sentence.

## Out of scope

- Building or evaluating a full coupled GCM forecast, or any CMIP-based transfer experiment.
- Predicting ENSO impacts (rainfall, fisheries, crop yields); only the SST index is modelled.
- Operational delivery (scheduling, uptime, latency guarantees).
- A new theory of ENSO; the conceptual models are used as they are.
