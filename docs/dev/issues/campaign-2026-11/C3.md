## Summary

A lattice of units occupying fixed positions, where the design variable is which neighbours are physically joined. The same population must deliver three different mechanical functions in sequence — high stiffness, high energy absorption, and a compliant load path — by re-forming its connections. The distinguishing requirement is reachability: a configuration is only a result if the structure can re-arrange into it without passing through a state that cannot carry the current load.

## Question

For a fixed population of units in a fixed arrangement, can a connectivity search find configurations meeting three different mechanical objectives, and is there a reconfiguration path between them along which the structure remains serviceable at every step?

## Why run it

- Plain topology optimisation answers "what is the best structure"; this asks "what is the best structure that the structure can become", which is the question that matters for anything that has to reconfigure while in use.
- Reachability is a cheap, honest novelty: it changes which optimum is reported, and it can be checked on the same finite-element model the optimisation already needs.
- The result is a limit map — objectives that are mutually reachable, objectives that are not — which is a better deliverable than a single impressive configuration.

## Physical model

**Mechanics.** Linear elasticity on a unit-cell network: each unit is a stiff node, each connection a beam or a solid ligament with its own axial, bending and shear stiffness. Global stiffness assembled from element matrices; the objectives are compliance under a stated load, the first natural frequency, and an absorbed-energy proxy (a prescribed displacement cycle with the hysteretic work in the connections).

**Constraints.** Connectivity per unit (maximum number of joints), geometric feasibility (no two connections crossing), and the requirement that the structure carry a minimum service load at every intermediate state.

**Reachability.** Define an elementary reconfiguration as adding or removing one connection while the load is applied. A path is admissible if every intermediate configuration satisfies the service-load constraint with a margin.

**Deliberately out of scope:** nonlinear contact between units, plasticity in the ligaments, and manufacturing tolerances. The energy-absorption objective is a linear-elastic proxy and is labelled as such.

## Geometry and inputs

A 3-D arrangement of units on a lattice (for example a body-centred or face-centred cubic packing), a candidate connection set between near neighbours, and a load case per objective. Unit spacing, ligament cross-section and material set the stiffness scale.

## Solver and engine

- Structural assembly and solve: `pinneapple_simulation.numerical_solvers.solid_fem`, `elasticity3d_fdm`, `plane_stress_fem`, `beam_fe`; `pinneapple_design.bricks` (`Assembly`, `analyse_assembly`) provides the existing statics-on-a-built-structure pattern to extend.
- Connectivity search: `pinneapple_design.topology` (SIMP machinery and optimisers) is the wrong tool for a discrete problem, so a discrete search — genetic or simulated annealing over the connection set — is the work item, with `pinneapple_design.design_optimizer` for the multi-objective part.
- Verification: modal and static re-analysis on a refined model; `pinneapple_analysis.verification.convergence`.
- Recording: `pinneapple_lab.experiment`.

## What is missing (the work)

1. **A discrete connectivity model**: units, candidate connections, and an element library with the stiffness of each connection type.
2. **A reachability search**: given two configurations, find a path of single-connection changes that keeps the service-load margin positive, or prove that none exists within the search's stated effort.
3. **Three objectives implemented on the same model**: compliance, first natural frequency, and the elastic cycle-energy proxy, so the three configurations are comparable.
4. **The reconfiguration cost model**: time and actuation energy per connection change, so a path that takes ten thousand operations is visible as such.
5. **The limit map generator**: for each pair of objectives, whether the transition is reachable and at what cost.

## Experiment protocol

1. Validate the unit-cell stiffness against a solid-element model of one cell; report the error and the homogenisation assumption.
2. Optimise each of the three objectives independently without the reachability constraint; record the three optima and their objective values on all three metrics (the cross-table).
3. Add the reachability constraint: find the best configuration of objective B reachable from the optimum of A, and report the loss relative to the unconstrained optimum.
4. Sweep the service-load margin and report where the reachable path disappears.
5. Compute budget: minutes per structural solve at this size, thousands of solves for the search — order 10^2 CPU-hours.

## Baselines, references and verification

- Unconstrained optimum per objective (the "if it could teleport" baseline) and the initial uniform lattice.
- Solid-element reference for the unit-cell stiffness.
- Load-case checks with `pinneapple_check`: equilibrium, boundary conditions, and a symmetry check on a symmetric configuration.
- A hand-designed configuration from `bricks` for one objective, as a sanity floor.

## Metrics

- Compliance, m/N, and the first natural frequency, Hz, per configuration.
- Absorbed elastic energy per cycle, J (proxy), per configuration.
- Cross-objective loss: relative loss in objective B when configuration B must be reachable from A.
- Reachability: boolean per objective pair, plus the number of connection changes on the path and the cumulative service-load margin along it.
- Reconfiguration cost: time, s, and actuation energy, J, for the path.

## Deliverables

- The connectivity model, the reachability search and the limit map.
- The three optima with the cross-objective table.
- The margin sweep showing where reachability disappears.
- An animation of one reconfiguration path with the margin plotted alongside, from the campaign video pipeline.

## Acceptance criteria

- Unit-cell stiffness matches the solid reference within the stated tolerance.
- Each of the three objectives is met to within a stated fraction of the unconstrained optimum.
- Every reported reconfiguration path keeps the service-load margin positive at every intermediate step, verified by re-solving each step, not interpolated.
- The limit map reports at least one pair of objectives that is not reachable at the stated margin, or states that all pairs are reachable and at what cost.
- Reconfiguration time and energy are reported for every accepted path.

## Realizability and evidence class

`PLAUSIBILITY_CLASS`: `extrapolated`. Discrete modular structures and reconfigurable lattices exist in research; a structure that safely reconfigures under load does not exist as a product. Axes: `mathematical_consistency` (equilibrium and symmetry checks, unit-cell reference), `numerical_stability` (mesh and element-count convergence), `physical_plausibility` (margin along the path, actuation cost), `uncertainty_sensitivity` (margin sweep). `experimental_validation` and `technological_feasibility` stay not assessed.

## Risks and failure modes

1. **A path exists only because the margin is measured on a linear model that would not survive the real transient.** Mitigation: state the quasi-static assumption, require the margin at every step, and add a factor on the required margin for the transient.
2. **The search reports "unreachable" because it did not search enough.** Mitigation: report the search effort and the best path found, and frame the result as "no path found within effort", not as impossibility.
3. **The elastic energy proxy is mistaken for absorption.** Mitigation: the label "elastic proxy" accompanies every number, and no damping or plasticity claim is made.
4. **Discrete search cost explodes** with the connection set. Mitigation: pruning by connectivity limits and a symmetry-reduced candidate set.
5. **The three objectives are not comparable** because the load cases differ. Mitigation: a single stated load case per objective, fixed before the search.

## Out of scope

- Actuator design for the connection changes.
- Fatigue and damage accumulation over many reconfigurations.
- Manufacturing of the units.
