## Summary

A fixed set of natural-language object descriptions is passed through the existing intent-to-design path, and each result is scored on three things: did the parser read the requirements correctly, did the resulting object pass its physics check, and is it buildable. The output is a success rate with its failure breakdown, compared against a hand-made CAD answer on a small subset. The deliverable is the score, not a demonstration, and the issue is written so that a low score is a complete result.

## Question

Across a fixed prompt set covering the templates the intent layer supports and a set it does not, what fraction of descriptions produces a verifiable and buildable design, and which failure mode — parse, physics or buildability — dominates?

## Why run it

- The intent layer already exists and already refuses out-of-scope requests, so the honest experiment is a measurement of its coverage, not a demonstration of a demo case that was chosen after it worked.
- A published rubric and a fixed prompt set make the number comparable across later versions, so the issue produces a benchmark that stays useful after it closes.
- The failure taxonomy is the most useful artefact: knowing that 40 percent of failures are a mis-assigned unit rather than a physics problem changes what to build next.

## Physical model

There is no single governing equation; the model is whatever each template's physics package is, and the experiment's discipline is to use the template's own verification rather than a new one. The templates available are a bracket (a loaded plate or beam with a stated span and load), a heat sink (a fin array with a stated power and allowable temperature rise), a glider wing (a lifting surface with a stated mass and speed), a loop car (a vehicle assembly), and a simple spring. Each carries a verification level — closed form, reduced or full — and the physics check for the benchmark is the template's verification at the level it declares.

The scoring rubric has three independent binary stages per prompt:

1. **Parse.** Every critical slot is filled with the correct value and dimension. A wrong number with a right dimension is a parse failure; a right number with a wrong dimension is a parse failure; an unfilled critical slot that was answered with a question is counted separately as a clarification, not a failure.
2. **Physics.** The generated design passes the template's verification at its declared level, with the acceptance thresholds the template already defines.
3. **Buildability.** The geometry satisfies a stated set of manufacturing rules: minimum wall thickness for the chosen process, no unsupported overhang beyond a stated angle for additive processes, no inaccessible internal feature, and the part fits a stated envelope.

Validity and omission: this measures a pipeline, not a general capability. The templates bound what can be recognised at all, so a prompt that is out of scope is expected to produce a refusal and is scored on whether it refuses rather than on whether it designs. No claim is made about arbitrary objects, about novices using the system, or about the quality of a design that passes — only that it verifies and can be made.

## Geometry and inputs

Prompt set: 60 prompts, fixed and versioned in the repository. Composition: 10 per supported template (50 total), written independently in three registers — a full engineering sentence with units, a terse phrase, and a sentence with the quantity expressed in different units or with a unit abbreviation — and 10 out-of-scope prompts that describe a plausible object the templates do not cover. Each prompt carries the reference interpretation: the slot values with their dimensions, written by hand before the run.

Buildability rules per process: a stated minimum wall for a machining process, and for an additive process a minimum wall, a maximum overhang angle and a minimum feature. The reference CAD answers cover 5 prompts, one per template, produced independently and scored on the same rubric.

## What is missing (the work)

1. **The versioned prompt set with reference interpretations**: `benchmarks/thoughtform/prompts.yaml` with 60 entries, each carrying the text, the register, the template or the out-of-scope label, and the reference slot values with dimensions. Written by hand and reviewed before any run; it must not be adjusted after seeing the results.
2. **A slot-level parser scorer**: compares the produced `RequirementSpec` against the reference interpretation, reporting per-slot agreement, dimension errors and unused numbers separately, since those three failures are different bugs.
3. **A manufacturing-rule checker**: `pinneapple_design/manufacturing/rules.py` with `check_buildable(geometry, process, rules)` returning pass or fail with the violated rule and the location. No manufacturing rule set exists in the library.
4. **A buildability reference per process**: the rule values with their source stated — a standard for additive design limits, and a stated shop capability for machining — so the threshold is not invented.
5. **A refusal scorer**: a separate metric for the out-of-scope prompts, which is a false-accept rate and a false-refusal rate, not part of the design success rate.
6. **A rubric implementation in the benchmark harness** that registers the three stages as `Check` instances so a run's report contains the breakdown, and a version string on the prompt set so later runs are comparable.

## Experiment protocol

1. Fix the prompt set and the reference interpretations, and record a hash of both before the run starts.
2. Run the deterministic parser only on all 60 prompts; record per-slot agreement, dimension errors, clarification requests and refusals.
3. Run the full pipeline on the 50 in-scope prompts, with the LLM path disabled and then enabled, so the deterministic and assisted paths are separated: 100 design runs.
4. Score each result on parse, physics and buildability; record the failure stage for every failure, and no more than one stage per prompt, taking the earliest failure.
5. The reference CAD answers: score the 5 hand-made designs on the same rubric, which is the achievable ceiling and not a competing method.
6. Repeat the whole design run with three seeds to establish determinism; any variance in the deterministic path is a defect and is reported as such.
7. Compute budget: seconds to minutes per design, dominated by the physics verification — order 10^0 to 10^1 CPU-hours.

## Baselines, references and verification

- The hand-made CAD answers are the ceiling: the pipeline cannot be expected to exceed them, and the gap is reported.
- The determinism check is a correctness requirement: the same prompt with the same seed must give the same design, and a difference indicates a non-determinism defect.
- The physics checks come from the templates and are not re-implemented; if a template's verification is wrong, the benchmark is measuring the wrong thing, and the report must state which verification levels were used.
- The unit parser is cross-checked against the unit table on a fixed list of 50 number-unit strings, so a dimension failure is attributable to the parser rather than to the template.
- Baselines the pipeline must beat: a null baseline that always refuses (high false-refusal, zero false-accept) and a naive baseline that always produces the first template's default design. Both numbers make the success rate interpretable.

## Metrics

- Parse success rate, percent, per template and per register.
- Physics verification success rate, percent, at the declared verification level.
- Buildability pass rate, percent, per manufacturing process.
- End-to-end success rate: all three stages pass, percent, with the failure-stage breakdown summing to the complement.
- False-accept rate and false-refusal rate on the out-of-scope prompts, percent.
- Determinism: the fraction of prompts with identical output across three seeds.
- Ceiling gap: the difference between the pipeline's end-to-end rate and the hand-made reference's rate on the 5 shared prompts.

## Deliverables

- The versioned prompt set and reference interpretations, with their hashes, as data files in the repository.
- The scorer, the manufacturing-rule checker and the rubric registration as importable code with tests.
- The benchmark report from `pinneapple_analysis.benchmark`, in its standard form, so the result is comparable with other benchmark runs.
- A table of every prompt with its three-stage outcome and, for failures, the failing slot or rule, as CSV.
- The failure taxonomy figure: failure stage against register and template.
- A `pinneapple_lab` manifest per run, with the prompt-set hash, the code revision and the seed.
- A report whose first paragraph gives the end-to-end success rate and the dominant failure stage.

## Acceptance criteria

- The prompt set has 60 entries with reference interpretations, and its hash is recorded before the run.
- The deterministic path produces identical output for identical prompts across three seeds, for 100 percent of prompts; a single mismatch is reported as a defect.
- Every prompt has an outcome at exactly one of the three stages, or a clarification or refusal, and the counts sum to the prompt total.
- The end-to-end success rate is reported per template and per register, not only in aggregate.
- The false-accept and false-refusal rates are both reported for the out-of-scope set.
- The five hand-made answers are scored on the same rubric and the ceiling is stated.
- The report does not omit any template on which the pipeline scores below 50 percent; a low score is reported with the same prominence as a high one.

## Realizability and evidence class

`PLAUSIBILITY_CLASS`: `established` as a measurement of an existing software pipeline; `extrapolated` for the claim that the measured rate transfers to prompts written by users rather than by the issue author, since the prompt set is written here and that is the study's main external-validity limitation; `hypothetical` for arbitrary object generation, which the template set does not attempt. Axes this run fills: `mathematical_consistency` (unit parsing against the unit table, determinism), `numerical_stability` (repeatability across seeds, verification-level consistency), `physical_plausibility` (the physics checks are the templates' own), `uncertainty_sensitivity` (the per-register breakdown and the ceiling comparison). `experimental_validation` in the sense of human users is not assessed. `technological_feasibility` is partly addressed by the manufacturing rules.

To move up one class, in order: (1) a prompt set written by users who did not see the templates, with a stated sampling procedure, since author-written prompts are the largest bias in this design; (2) a demonstrated build of at least one generated design, since the buildability rules are a proxy for a manufacturing outcome; (3) coverage of object classes beyond the five templates, which is a scope question and not a measurement; (4) a quality criterion beyond pass-fail, since a design can verify and still be poor. Item 1 is the one this experiment cannot do for itself.

## Risks and failure modes

1. **The prompt set is tuned until the score is acceptable.** Mitigation: the set and its references are hashed and frozen before the run, and any later change creates a new version rather than an edit.
2. **Failures are attributed to the last stage rather than the first.** Mitigation: the rubric assigns each prompt to its earliest failing stage, which is the only attribution that identifies a cause.
3. **The buildability rules are invented and the pass rate is meaningless.** Mitigation: every rule value has a stated source, and the rule set is reported with the results.
4. **The out-of-scope prompts are scored as failures rather than as refusal tests.** Mitigation: the refusal metrics are separate, with separate acceptance criteria.
5. **The comparison with hand-made CAD is on five prompts and is over-interpreted.** Mitigation: it is labelled a ceiling check, its sample size is stated, and no statistical claim is made from it.

## Out of scope

- Training, fine-tuning or improving the intent layer; this issue measures and does not modify.
- Object classes outside the five templates.
- Manufacturability beyond the stated rule set, including cost, tolerance stack-up and assembly.
- Any claim about user experience, learning curve or productivity.
