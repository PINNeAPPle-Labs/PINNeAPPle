## Summary

Every experiment in this campaign ends in a video, and a video is the easiest artefact in engineering to fake. This issue builds the shared pipeline that makes the opposite claim checkable: a solver trajectory (mesh or point cloud plus fields over time) goes in, and what comes out is an image sequence, a video, and a frame manifest in which every frame carries the case id, the solver, the git commit, the input hash and the field statistics it was rendered from. A viewer can then take any frame, re-project it against the stored arrays, and see whether it matches. The pieces exist — Cycles rendering from NumPy, PLY sequence export, the digital-twin scene format, dashboard video, and a physics checker for rendered video — but they are separate tools with no shared contract.

## Question

Can a rendered frame be tied to its solver output tightly enough that an independent reader can verify the video is a visualisation of a computation and not an illustration, at a cost of a few CPU-hours per minute of footage?

## Why run it

- Without this, no experiment in the campaign can make a claim about its own render, and the campaign's whole proposition — the visual is the evidence — collapses into "trust the animation".
- It is shared infrastructure: one pipeline serves the ENSO plume, the topology-optimised manifold, the convection cell, the terahertz-scale speculation renders, and everything in between.
- It forces the honest exclusions: a frame that cannot be traced has to be either regenerated or labelled as an illustration, and the pipeline should make the second option visibly expensive.

## Physical model

The pipeline has no physics of its own; it consumes the output of one. What it does have is a set of rendering contracts that must be defined rather than assumed:

- **Field-to-colour mapping.** A named, versioned colour map per field, with a stored range (min, max, and the statistic that defines them), so the same field looks the same in every frame of every experiment. Sequential fields use a perceptually uniform map; diverging fields (a pressure anomaly, a stress sign change) use a diverging map centred on a stored value.
- **Geometry representability.** A point cloud is not a surface. The pipeline must state, per experiment, whether the render shows the mesh the solver used, an extracted isosurface, or glyphs on sample points, because the three have different evidentiary weight.
- **Scale and units.** A scale bar, an axis triad and a legend with units in every frame, drawn from the scene manifest rather than typed by hand.
- **Temporal fidelity.** Frame index maps to solver time through a stored table; no frame interpolation is allowed without being flagged, since an interpolated frame is not a solver state.

## Geometry and inputs

Inputs: a solver trajectory in one of the two interchange forms already supported — a scene directory in the `pinneapple_twin3d.scene` layout (`scene.json`, `geometry.glb`, `fields.bin`) or a numbered `.ply` sequence as written by `pinneapple_blender.export`. Additional inputs: a camera path specification (keyframes with location, look-at, focal length), a render budget, and the experiment's manifest from `pinneapple_lab`. Geometry simplification for rendering is allowed and must be recorded (a decimated mesh is a different artefact from the solver mesh, and the manifest says which was rendered).

## Solver and engine

- Rendering: `pinneapple_blender.cycles.CyclesScene` (in-process `bpy`, `add_surface`, `add_plane`, `camera`, `render`, `render_frames`, `frames_to_video`) as the primary path, with `pinneapple_blender.render.build_scene` (headless Blender subprocess) for scenes that need the full Blender feature set.
- Geometry exchange: `pinneapple_blender.export` (PLY sequence), `pinneapple_twin3d.scene.export` (`glb`, `fields.bin`, `with_viewer=True`, `usd=True`).
- Lightweight fallbacks: `pinneapple_twin3d` bundled web viewer and `pp.dashboard.Dashboard.to_video(gif=...)`, for runs where no Blender installation is available — the fallback must produce the same manifest, only lower fidelity.
- Compositing and encoding: ffmpeg through `frames_to_video`.
- Verification: `pinneapple_worldmodel.physical_world.physics_checks(video)` for the checks that can be run on pixels, plus the re-projection check added here.

## What already exists in PINNeAPPle (verified)

- `pinneapple_blender.cycles`: scene from NumPy arrays, surfaces from height grids, tubes along curves, point clouds, planes, text, camera and lights, `render`, `render_frames`, `frames_to_video`, `available()`.
- `pinneapple_blender.export`: result → numbered `.ply` sequence, with the per-vertex fields as properties.
- `pinneapple_blender.render.build_scene`: headless Blender through `blender --background --python`, with the add-on `import_pinneapple_sequence.py`.
- `pinneapple_twin3d.scene`: `scene.json` manifest, `geometry.glb`, `fields.bin`, bundled viewer, OpenUSD export with `add_physics`/`set_gravity`; `pinneapple_twin3d.gallery`, `.openfoam`, `.primitives`, `.serve`.
- `pp.dashboard.Dashboard(...).to_video(gif=...)`, `pp.viz.field_view(mesh, fields, deform=, markers=)`.
- `pinneapple_tools.nvidia.omniverse.FieldStage` for the OpenUSD/Omniverse variant of the same scene.
- `pinneapple_worldmodel.physical_world.physics_checks(video)` and `.corrupt(video, kind)` — a checker and an adversarially corrupted-video generator, which is exactly the negative control this pipeline needs.
- `pinneapple_lab.experiment(...)` + `ex.add_file(...)` for attaching the movie to the experiment manifest.

## What is missing (the work)

1. **`FrameManifest`** (proposed: `pinneapple_blender/provenance.py`): one record per frame with case id, solver name and version, git commit, input hash, field hash, colour map id and range, camera parameters, render settings, and the source array digest. Serialised as JSON Lines next to the frames, and hashed as a whole.
2. **A camera-path layer**: keyframes, easing, and a deterministic sampling so a re-render of the same scene from the same specification produces the same frames.
3. **A colour-map contract**: named maps with fixed ranges registered per experiment, and a check that a frame's legend matches its manifest.
4. **Re-projection verification**: for a sample of frames, project the rendered geometry back to image space and compare a blurred silhouette and a few field values at known points against the stored arrays; report the pixel disagreement as a number. This is the check that turns "the video came from the data" into something a reader can test.
5. **A budget model**: frames, samples per frame, resolution, estimated wall-clock and disk; a dry-run mode that prints the estimate and refuses an over-budget render without an explicit override.
6. **The fallback path**: the same manifest and the same legends from the web viewer and the dashboard, so a no-Blender environment degrades resolution, not provenance.
7. **A refusal rule**: the pipeline exits non-zero if any frame record is missing a provenance field, and the failure message names the frames — no silent "illustration" frames in a campaign render.

## Experiment protocol

The pipeline is validated on three existing cases rather than on a new one, because the point is fidelity to work already committed:

1. **ENSO case study** — the 1997/98 plume the existing study already renders; re-render through the new pipeline and check that the frame count, the time mapping and the field ranges match the committed figures within the stated tolerance.
2. **An OpenFOAM case** — a field from `pinneapple_twin3d.openfoam` (an existing case, e.g. the pipe-bend or cylinder wake output), to exercise mesh surfaces rather than point clouds.
3. **A synthetic negative control** — a video generated by `pinneapple_worldmodel.physical_world.corrupt(video, kind)` from the honest render; the re-projection check must reject the corrupted variants and accept the honest one. This is the acceptance test that matters.

Budget: 30 s per minute of 1080p footage at 64 samples, CPU-only Cycles, is the target order of magnitude; a 60-frame 960x540 sequence should complete in minutes on a laptop.

## Baselines, references and verification

- Reference for the ENSO render: the existing committed figures and the existing Blender clip, frame by frame, with the disagreement reported rather than smoothed over.
- Reference for the OpenFOAM case: the field statistics that `pinneapple_twin3d` writes into `scene.json` (min/max/mean per field per step) recomputed from the arrays and from the frames' stored ranges.
- Negative control: the corrupted-video variants must fail the re-projection check. If they pass, the check is too weak and the issue is not done.
- The `physics_checks(video)` results are reported alongside, as a second, independent signal.

## Metrics

- Provenance completeness: fraction of frames with all fields populated; must be 1.0.
- Re-projection disagreement: mean absolute pixel difference on a 32×32 low-frequency version of the frame, plus the maximum disagreement at the sampled field points, dimensionless and in field units respectively.
- Colour-range fidelity: reported field range versus rendered legend range, relative error.
- Cost: wall-clock seconds per rendered frame at a stated resolution and sample count; peak memory.
- Determinism: byte-identical frames across two runs with the same seed and settings (or the fraction that differ, which for Cycles is expected to be non-zero unless determinism is forced).

## Deliverables

- The `pinneapple_blender.provenance` module with `FrameManifest`, the camera-path layer, the colour-map registry and the re-projection checker, plus tests.
- A conversion tool from either input form (scene directory or PLY sequence) to a provenance-complete render.
- Three worked renders (ENSO case, OpenFOAM case, negative control) with their manifests committed under an `examples/` folder, and the movie attached through `pinneapple_lab`.
- A short guide, `docs/guides/scientific_video.md`, with the contract, the budget table and the failure modes.

## Acceptance criteria

- Every frame of every accepted render has a complete manifest record; the pipeline exits non-zero otherwise.
- The negative control is rejected: corrupted videos produce a re-projection disagreement at least a stated factor above the honest render's.
- The ENSO re-render reproduces the committed figure field ranges to within 1 % and the frame-time mapping exactly.
- Two runs with the same settings produce frames whose low-frequency content agrees to within the stated tolerance, with the residual reported.
- The no-Blender fallback produces the same manifest fields for the same case, with fidelity differences quantified rather than described.
- Rendering a case whose solver output is missing a required field fails with a message naming the missing field, not with a blank frame.

## Realizability and evidence class

This is infrastructure; its evidence class is `established` in the sense that rendering and provenance tracking are ordinary engineering, and the risk is relevance, not feasibility. Evidence axes: `numerical_stability` (determinism and re-projection reproducibility), `mathematical_consistency` (the re-projection check as a testable statement about the mapping from arrays to pixels), `uncertainty_sensitivity` (how much pixel disagreement the tolerance allows). `physical_plausibility` is inherited from the physics that produced the fields, not from this pipeline; `experimental_validation` and `technological_feasibility` are not assessed here.

## Risks and failure modes

1. **The re-projection check passes trivially** because it compares the frame to the same arrays that produced it. Mitigation: the negative-control requirement, and sampling the check on a decimated copy of the geometry so the check cannot be satisfied by the renderer echoing its input.
2. **Blender absence becomes a silent downgrade.** Mitigation: the manifest is mandatory on every path, and the guide states which experiments were rendered on the fallback.
3. **Provenance theatre**: a manifest filled with hashes that nobody can use. Mitigation: the manifest must be sufficient to re-run the frame, and one test does exactly that for a single frame.
4. **Codec loss** destroying the measurable content. Mitigation: the check runs on the frames, not on the encoded video; the video is for humans, the frames are for the record.
5. **Cost blow-up** on the more ambitious renders (large meshes, volumetric fields). Mitigation: the budget model with an explicit override, and a documented level-of-detail policy that is recorded in the manifest as a fidelity choice.

## Out of scope

- Photorealistic look development, motion design or sound.
- Interactive viewing (the `pinneapple_twin3d` viewer already covers that).
- Distributed rendering or a farm; single-machine CPU rendering is the target.
- Rendering fields the solver did not output (no artistic volumetric additions).
